# spine-godot — Godot 4.7 support (design)

Date: 2026-06-22
Status: approved (brainstorming), pending implementation plan
Branch: `spine-godot-4.7-support` (off `4.3`)

## Goal

Make spine-godot build and run on **Godot 4.7** in **both** build configurations
(the engine **module** and the **GDExtension**), as a *multi-version* addition —
**4.6 stays supported** — and add **4.7-stable** to CI. The codebase already
multi-versions via `#if ... VERSION_MINOR >= N` guards (4.0–4.6), so 4.7 is a new
tier in an established pattern, not a baseline move.

This also fixes the **currently-red 4.6 GDExtension CI** as a side effect (same
root cause — see §1).

Non-goals: dropping 4.6; the Godot 3.6 `godot-editor-windows` Python-3.14 CI
failure (separate infra issue, see §5); two-color tint / screen blend (unchanged).

## Context / constraints

- **Godot 4.7-stable is released** (engine tag exists upstream).
- **godot-cpp has no `4.6` or `4.7` branch *or* tag** — its latest release branch
  and tag are both `4.5`. So a GDExtension targeting 4.6 or 4.7 has no
  version-matched godot-cpp; it must use either godot-cpp `master` or an older
  stable godot-cpp via forward-compatibility.
- Today `setup-extension.sh` falls back to godot-cpp **`master`** when no
  major.minor branch matches. godot-cpp `master` recently introduced a breaking
  change (`memnew(T)` for a `RefCounted` `T` now returns `Ref<T>`, not a raw
  pointer), which breaks existing `SpineAtlasResource.cpp` (`JSON *json = memnew(JSON)`)
  — this is why the 4.6 GDExtension CI is red. It is **not** caused by the 3D
  feature; it fails on the `4.3` base too.
- spine-godot's `.gdextension` declares `compatibility_minimum = "4.1"`; the
  extension uses RenderingServer / mesh / scene APIs that long predate 4.5. We
  already build the extension against **godot-cpp 4.5** locally and run it in the
  4.6 editor (forward-compat verified).
- The **module** build compiles against the actual Godot version's source, so it
  gets the real `VERSION_MINOR` and full 4.7 engine API.
- Dev machine is Windows; build costs differ sharply by build type (see §4).

## Design

### §1 — GDExtension: godot-cpp version strategy (the key change)

Change `spine-godot/build/setup-extension.sh` so that when there is **no
version-matched godot-cpp branch/tag** for the target engine version, it falls
back to the **latest stable godot-cpp tag** (currently `4.5-stable`) instead of
`master`.

Rationale:

- A godot-cpp-4.5-built extension loads in **4.5, 4.6 and 4.7** by
  forward-compatibility (godot-cpp's `compatibility_minimum` + compat-hash
  mechanism). We already rely on this for 4.6.
- It is **reproducible** (a real release tag, not a moving `master`).
- It needs **no `memnew`/master compat churn** — the 4.5 API has the old
  raw-pointer `memnew`, so the existing code compiles unchanged.
- It **greens the 4.6 GDExtension CI** and makes the 4.7 GDExtension build pass
  for the same reason.
- It is **self-upgrading**: when godot-cpp publishes a `4.6`/`4.7` branch or tag,
  the existing exact-match path selects it automatically with no further change.

Trade-off accepted: the extension is built at the 4.5 API level, so it cannot use
4.6/4.7-only **extension** APIs. spine-godot uses none (it targets a 4.1
baseline), so this is a non-issue. Concretely, in the extension build
`VERSION_MINOR == 5`, so any `#if VERSION_MINOR >= 6` block compiles out of the
extension — this matches what we already do locally (we build the extension
against godot-cpp 4.5), so it is not a regression: the prior `master` extension
build never succeeded.

Mechanism: the fallback uses a single, clearly-named "latest stable godot-cpp
tag" value (e.g. `4.5-stable`) in `setup-extension.sh`, cloned with `-b <tag>`
exactly as today. (No move to pinning a `master` SHA; that option is recorded
here only as the rejected alternative — it would reintroduce master's breaking
changes and risk a newer-godot-cpp-in-older-engine load mismatch.)

### §2 — Module build (4.7): engine API compatibility

Build the module against Godot 4.7 source and fix any 4.7 *engine* API changes
that break compilation, discovered empirically via CI (and/or a local module
build). Fix strategy, in order of preference:

1. **Version-agnostic rewrite** that compiles on all supported versions
   (e.g. `Ref<JSON> json = memnew(JSON); ... json->...;` works whether `memnew`
   returns a raw pointer or a `Ref<>`; drop any paired manual `memdelete`).
2. **`#if VERSION_MINOR >= 7` (or `VERSION_MAJOR/MINOR`) guards** only where an
   API genuinely diverges and no single spelling compiles on both.

Note: the `memnew→Ref<>` change may be **godot-cpp-only**; the engine's `memnew`
may be unchanged, in which case the module needs no `memnew` work. CI against
4.7 source is the source of truth for the actual breakage list.

### §3 — CI matrix

Add **`4.7-stable`** (confirm the exact released patch tag during implementation;
`4.7-stable` exists upstream) to the build matrices, keeping `4.6.2-stable`:

- `spine-godot-v4-all.yml` (module, all platforms)
- `spine-godot-extension-v4-all.yml` (GDExtension, all platforms)

No `pull_request` triggers exist; CI runs on push (and these are reusable
`workflow_call` matrices). Confirm the exact 4.7 patch tag during implementation.

### §4 — Verification strategy

- **GDExtension (fast, local):** build against godot-cpp 4.5, install into the
  example, load it in a downloaded **Godot 4.7 editor binary**, and run the
  example project (including a `SpineSprite3D` scene) to confirm it loads and
  renders in 4.7. Iterate here for all extension-side fixes.
- **Module 4.7 + all cross-platform targets:** verify via **CI** (a from-source
  4.7 module build is 30–90 min locally). Read CI failure logs, fix, repeat.
- Keep 4.6 green throughout (don't regress the existing tier).

### §5 — Out of scope (follow-ups)

- Godot 3.6 `godot-editor-windows` failing in SCons MSVC detection under the
  runner's Python 3.14 — a separate, repo-wide CI-infra issue (fix: pin Python
  ≤3.12 for that job). Not part of 4.7 support.

## Success criteria

1. `setup-extension.sh` selects godot-cpp `4.5-stable` (not `master`) for engine
   versions lacking a matched godot-cpp branch/tag; auto-selects an exact match
   when one exists.
2. GDExtension builds against godot-cpp 4.5 and **loads + runs in the Godot 4.7
   editor** (example incl. `SpineSprite3D` renders).
3. Module builds against **Godot 4.7** source on CI across all platforms.
4. CI matrix includes **`4.7-stable`** for module + extension, and the **4.6
   GDExtension build is green** again.
5. 4.6 remains fully supported (no regression).
6. New code changes are clang-format-18 clean (matches `format-check-cpp`).

## Risks

- **Forward-compat 4.5→4.7 load:** a 4.5-built extension might hit a changed
  method compat-hash in 4.7. Mitigated by godot-cpp's compat system and verified
  by loading in the 4.7 editor locally before relying on CI.
- **Unknown 4.7 module breakages:** beyond `memnew`, 4.7 source may change other
  APIs. Surfaced and fixed iteratively via CI; version-agnostic fixes preferred
  to avoid widening the guard surface.
- **godot-cpp `master` drift (avoided):** by not using `master`, CI no longer
  depends on a moving target.
